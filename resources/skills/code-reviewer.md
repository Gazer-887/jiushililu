# 代码评审

## 基本规则

- 问题定位一律用**新版本行号**（diff 右侧）；多行问题给 `[起, 止]`
- **先给证据再给结论**：评论里引用真实代码行，不凭印象
- 评**正确性、边界条件、遗漏的用例、错误处理、安全隐患**；不评纯风格（那是格式化工具的事）

## 步骤

### 一、定范围

用户指定了范围（某文件 / 与某分支对比 / 未提交改动）就按指定的；没指定就先问清，别自作主张审全库。

### 二、收证据（必做）

先读相关源码再开口：搜索函数定义与调用方、读改动涉及的完整文件。**只看 diff 就评论 = 隔着门缝看病。**

### 三、推断作者意图

从改动模式（加错误处理？换算法？重构变量名？）推断**这次改动想干什么**，并一句话说破：
> 意图：为 process_user 补空值防护，防止下游空指针。

后续所有评论都以此为背景——**偏离意图的"问题"要么是真 bug，要么是你理解错了意图**，先分清这个。

### 四、结构化输出

按严重度分组，每条包含：位置（新行号）、问题、为什么是问题（触发场景）、建议修法。

- **必须修**：会出错、会丢数据、安全洞
- **建议**：边界更稳的写法、遗漏的测试
- **疑问**：拿不准意图的地方，问而不是断言

## 反模式

- **风格洁癖刷存在感** —— 命名/空格类的意见淹没了真问题
- **"建议加注释"式空评论** —— 每条评论都要能执行
- **只赞不评** —— 没发现问题就说"审了什么、确认了什么"，而不是含糊的"LGTM"
