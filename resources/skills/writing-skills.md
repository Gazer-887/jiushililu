# 写技能

## 什么值得成为技能

**值得**：这个方法你当初不是一眼就会的、跨项目还会再用、模式足够通用、别人也能受益。

**不值得**：一次性的解法、别处已有标准文档的通识、只属于某个项目的约定（那是项目规则文件的事）、能用校验/正则自动化强制的机械约束（**自动化它，别写文章**）。

## 技能是参考，不是故事

技能 = 可复用的方法、模式、工具、参考。
技能 ≠ "我当时怎么解决这个问题"的叙事。写之前问：**下次遇到同类事，照着这条能不能直接做？**不能，就改写成能，或不写。

## 写之前先写"失败基线"

改技能就是给流程文档做 TDD：

| TDD | 写技能 |
|---|---|
| 测试用例 | 一个压力场景（让一个没有此技能的执行者去做） |
| RED | 观察它没有技能时**怎么失败、用什么借口合理化** |
| GREEN | 写技能，针对性堵住那些失败点 |
| REFACTOR | 新借口出现 → 补反制 → 再验 |

**没见过失败，就不知道该教什么。**先跑基线再写，写出来才有的放矢。

## description 是触发器（最关键的一行）

- 写清**何时用**：具体到场景信号（"打算说做完了之前""遇到任何 bug 提修法之前"）
- 写清**何时不该用**：防它乱触发抢戏
- 让同类的技能之间**边界不重叠**——两个技能抢同一个场景，等于都没写好

## 结构纪律

- 一个技能一个主题；支撑材料才建附属文件，能不建就不建
- 语气直接、可执行："做 X"，不是"通常建议考虑 X"
- 反模式段落要写**具体的错误样子**，不写抽象告诫
