# 系统化排查

## 铁律

**没有根因调查，不许动手修。**

乱修浪费时间、制造新 bug；快补丁掩盖真问题。修症状 = 修了个寂寞。

## 什么时候用

一切技术异常：测试失败、线上 bug、行为不符预期、性能劣化、构建失败、集成不通。

**尤其**要在这些时刻用：时间紧（越紧越想猜）、"就改一行"看起来很明显、已经试了几种修法都没好、上一次修复没生效。

## 四阶段（每阶段完成才准进下一阶段）

### 一、根因调查

1. **细读报错**：错误信息、堆栈、行号、错误码——往往答案就写在里面，别跳过
2. **稳定复现**：能稳定触发吗？精确步骤是什么？不能复现 → 继续收集信息，**不许猜**
3. **查最近改动**：这次之前什么变了？（diff、新依赖、配置、环境差异）

### 二、模式分析

4. **找首个失败点**：日志里看**第一个**失败，后面的常是它的连锁——不要从最后一个红叉往回猜
5. **对照工作版本**：什么能正常工作？坏例与好例差在哪？

### 三、最小假设验证

6. **一次一个变量**：形成最小假设，改一处验证一次。同时改三个东西 = 你永远不知道哪个起了作用
7. **预期先写下来**：验证前先写"如果假设成立，我应该看到 X"——看到 X 之外的东西就是假设错了

### 四、修复 + 回归

8. **修根因，不修症状**：修完必须重跑原始失败场景确认
9. **补回归**：为这个 bug 写一条测试，防止它回来

## 语气要求

"我还没找到根因，目前知道的是……"是合格回答。
"我试了几种改法"不是——那叫乱枪打鸟。
