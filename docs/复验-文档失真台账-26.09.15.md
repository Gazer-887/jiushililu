## 二、复验方法（与前几次的关键差别）

### 以往做法
「PLAN/ 状态行 × NOTEBOOK/progress.md × src/ 三方交叉」——读的是**计划自己怎么说**。
缺陷：三份文档可能**一起过时**，交叉验证就失效（今天得到证实：汇表、plan12、progress.md
三处对同一件事给出同样的错误答案）。

### 本次做法
**不读计划怎么写的，直接到源码找符号**，分层取证：

| 层级 | 证据强度 | 做法 |
|---|:--:|---|
| ① 文件存在性 | 弱 | `test -f` |
| ② 导出符号 | 中 | `grep "export function\|export type"` |
| ③ IPC 通道 + 调用点 | **强** | grep 定义 + grep 谁 import / 谁调用 |
| ④ **反向检查** | **最高产出** | 查「待实现」清单里**是否藏着已交付的** |

**第 ④ 层是本次最大的方法论收获** —— 6 条严重问题里，有 4 条是这样挖出来的。
正向验证（"标记完成的真的是否完成"）只证明没虚报；
**反向验证（"标记未完成的真的是否未完成"）才抓得出漏报**。

### 分组原则
- **单文件 > 90 KB 独占一组**（plan8 / plan19 / progress.md / learnings.md / 术语词典 / diary-09.12）
- 其余按主题合并至约 130 KB/组

## 三、严重问题（6 类）

### 3.1 ~~编造的提交号~~ → **实为「引用失效」**（本次复验自身的一次误判纠正）

> ⚠️ **本节结论于 2026-09-16 凌晨推翻并改写。** 原标题为「【硬红线】编造的提交号」。
> **原结论是错的。** 保留完整推翻过程 —— 过程比结论更值得留档。

**原判断（子代理报出）**

| 项 | 内容 |
|---|---|
| 位置 | `NOTEBOOK/progress.md`（原记 L1011，加注后行号后移） |
| 原文 | 「git init + 首次提交 `c791451`」 |
| 子代理实测 | `git rev-list` 显示根提交为 **`c6cdb2b`**；全库 `grep` 对 `c791451` **零命中** |
| 子代理结论 | **引用编造**（违反 AGENTS.md「绝不编造数字」） |

**复核推翻（WorkBuddy 端）**

顺着「本项目做过 `git filter-repo` 历史重写」这条线索往下查，在
`.git/filter-repo/commit-map` 找到决定性证据：

```
c791451c01017cb1c8a555d02f2a00411371a522  c6cdb2bca6f8c7a84b2abca45ad5fa907d0204b6
       ↑ 重写前                                      ↑ 重写后（当前有效）
```

**`c791451` 正是 2026-09-10 署名修正重写前的真实根提交 SHA。**
（映射表恰好 11 行，与当时被重写的 11 个提交吻合。）

**真实性质**：**不是编造，是「引用失效」** —— 历史被合法改写后，旧坐标自然失准。
两者必须分清：前者是**伪造**（诚信问题）；后者是**正常的工程后果**（不需问责，只需加注）。

**实际影响范围（用映射表全库反扫）**

正式文档中**只有 `progress.md` 命中，共 6 处**，全部集中在 2026-09-09（P0 首日）那段日志；
`PLAN/` `DIARY/` `docs/` `README` `AGENTS.md` `CHANGELOG.md` **零命中**。

**处置**：在该段加「SHA 说明」块（含 11 条旧→新完整映射），**不改原文** ——
原文记录的是当时的事实，篡改历史记录比留着失效引用更糟。

> **★ 本次复验最有价值的一条元教训：**
> **「看起来是假的」不等于「是假的」。**
>
> 子代理的判断在它的视野内完全合理（那个 SHA 在**当前**仓库确实不存在），
> 但它**不知道历史被重写过**这个前提 —— 于是把「旧坐标」读成了「伪造坐标」。
>
> 这与本项目 `AGENTS.md` 里那句「**『碰巧对了』是最危险的正确**」互为镜像：
> **「看着像错的」也最可能是最危险的错判** —— 因为它看起来太有说服力，
> 以至于没人会去复核。本次是靠"再往下查一层"才没把错误结论写进正式文档。
>
> **由此新增一条核验规矩**：凡**历史重写过**的仓库，核验提交号时必须
> **先查 `commit-map`**，再判「存在 / 不存在」。

## 七、规律与根因（本次最有价值的部分）

失真是**成簇分布**的，不是随机的。归纳出四条规律：

### 规律 1：「等人拍板的条目」会永远漂着

- **样本**：首屏水印。自 0.10.0 写进 R7 待办，标着「（用户未定）」，**漂了三天**，
  直到 2026-09-15 用户一句话砍掉 —— 期间**没有任何机制会去问它一句**。
- **机理**：这类条目的状态由**外部事件**决定，但它自己不产生提醒。
- **建议**：凡写「待圈定 / 待用户决定 / 待拍板」的行，**必须自带一个「问过没有」的时间戳**。

### 规律 2：「以为别人会顺带更新」的文档必然落后

- **样本**：`docs/功能汇表.md` 停在 0.13.35，落后 **13 版**，
  而同日期的 `CHANGELOG.md` / `README.md` 都是新的。
- **机理**：CHANGELOG 和 README **每个版本必须动**（有硬性触发点），
  汇表没有 → **版本推进对它不产生任何压力**。
- **建议**：给汇表挂一个**与 CHANGELOG 同源的更新触发点**（如批收口时同步），
  或干脆取消这张表、改为从 CHANGELOG 自动生成。

### 规律 3：失真长在「没人回头看的地方」

- 有评审闭环的（problem / decisions / learnings）**干净**；
- 没人回看的（各 plan 的正文中段、DIARY 专题）**堆积**。

### 规律 4：**大转向会留下跨文件的残片**

node-pty 转向（2026-09-13，伪终端 → 真 PTY）在**至少 5 个文件**留下未清理的旧结论：

| 文件 | 残片 |
|---|---|
| `.workbuddy/memory/MEMORY.md` | 「不用 node-pty」→ ✅ 已于 2026-09-15 修正 |
| `plan14` §四 L454 | 选型汇总表仍「❌ node-pty」 |
| `术语词典` L627 | xterm.js 词条「不上 node-pty」 |
| `plan1` L49/L143 | 「失败降级 child_process」未标反转 |
| `plan2` L35 | 「改用 child_process 起步」未标反转 |
| `diary-26.09.12` | 全篇零 node-pty 记录 |

**机理**：转向时大家在**结论处**（顶部转向块、新章节）改得很认真，
但**不会回头扫全库**找旧结论。而旧结论散落在表格、词条、风险清单、修订史里 ——
**恰恰是最像"现行有效内容"的位置**。

> **建议**：任何**推翻性决策**（不是补充，是反转）应当附带一个动作：
> **全库 grep 被推翻的关键词**（如 `node-pty`、`child_process`、`Tailwind`），
> 逐处判定并标注。本次 `Tailwind` 也是同类（plan1 L47 未标作废）。

## 九、方法论沉淀（供下次复验直接复用）

### 9.1 检查清单（四层，按产出效率排序 —— 第 ② 层最高）

| 层 | 检查项 | 手段 |
|---|---|---|
| ① | 编号完整性与双向指针 | grep 编号 → 查重复/跳号；取代关系查两头 |
| ② | **提交号全量核验** | 抓全部 7–8 位十六进制串 → `git cat-file -t <sha>` **逐个**验 |
| ③ | 状态矛盾 | 标题↔正文 / checkbox / 「待拍板」vs 已有结论 / 图↔条目清单 |
| ④ | 数据出处 | 找无来源却写得像实测的数字 |

**第 ② 层用极小成本拿到了唯一一条硬红线**（`c791451`）。**建议固化为常规动作。**

### 9.2 分组原则

- 单文件 > 90 KB **独占一组**
- 其余按主题合并至约 130 KB/组
- 12 组左右可并行

### 9.3 prompt 要点（写给子代理的）

1. **必须给背景** —— 子代理看不到主会话，要交代项目是什么、已知的失真案例长什么样
2. **给出已知事实** —— 避免它重复验证（省 token，也防止它把已确认的事实又当新发现报一遍）
3. **明确「只读、禁止修改」**
4. **限定输出字数** —— 否则会复述文件内容
5. **要求给真实行号**
6. **要求回答指定问题** —— 例如「编号是否连续唯一？提交号是否全部真实？」

### 9.4 本项目最该常查的三处

1. `NOTEBOOK/progress.md` 的**摘要层**（「一页纸」「待办」「下一步」）
   —— 正文会更新，摘要层最容易停滞
2. 各 plan 的**正文中段**（表格、选型汇总、风险清单、修订史）
   —— 顶部转向块和新章节都改得很认真，中段最容易被漏
3. **所有「待用户决定」的条目** —— 查「问过没有」，别让它永远漂
