## 一、结论先行

**它把软件做出来了，但"借用户的手"跑起来的——而它本来不必如此。**

- 交付物真实存在：15 个文件、69,515 字节，后端 + 前端 + 自检脚本 + 启停脚本 + README，
  服务真实监听 `127.0.0.1:8787`，自检 **27 项：通过 26、跳过 1、失败 0**。
- **但它没有走"能直接执行命令"的那条路。** 本轮它以默认主会话运行，而默认主会话的工具集不含
  `run_command`；只要绑定内置的 `code-executor` Agent 就有这个能力，**且完全访问档下它不弹确认卡**。
  它没意识到这一点，也没提示我换 Agent，于是绕道桌面控制 MCP —— 那里既有白名单过滤又有危险门控，
  每一步都要人点，最终 5 次因超时被拒。
- **所以本轮测出的不是"产品没有能力"，而是"能力存在但不可发现"**——这比缺功能更值得修。

**卡顿：本次未复现，且这次有分量的证据链是完整的。** 报告初稿时探针还拿不到"是否在响"的
运行期证据（§5.3）；该缺口已用**含心跳的新包重跑一轮**闭合（§5.4）——
**15 分钟里 2994 笔同步块被如实记账，同期停滞 0 条、慢块 0 条。**
⇒ 可以说到满：**这版在我真人操作的负载下没有卡。**
⇒ 但仍不写作"卡顿已修好"：真凶至今一次都没被复现过，被排除的只是"普通同步文件 IO"这一类。

### 3.2 自检结果：**同一份日志有两个版本，差异本身就是发现**

它一共跑了两次自检，第二次**覆写**了第一次。两版结尾不同：

| | 中途版（03:35 读到） | **最终版（盘上现存）** |
|---|---|---|
| 汇总 | 共 26 项，通过 25，**失败 1** | 共 27 项，通过 26，**跳过 1，失败 0** |
| 真实模型那项 | `[FAIL] 真实模型调用 → 未配置 API Key —— 跳过` | `[SKIP] 真实模型调用 → 未配置 API Key，跳过。到界面左下角「设置」填入密钥后重跑本自检即可。` |
| 结论行 | `自检结果：存在问题，见上` | **`自检结果：全部通过`** |
| 退出码 | `exit=1` | `exit=0` |

**怎么读这件事（两面都要说）**：
- ✅ 它**没有伪造**：跳过项写明了原因和补救路径，`[SKIP]` 与 `[PASS]` 分得清清楚楚。
- ⚠️ 但**汇总措辞过头**：一项从未验证的能力被计入"全部通过"、退出码 0。
  对一份"交付即验收"的自检脚本来说，**跳过 ≠ 通过**，`exit=0` 会让任何自动化流程把它当绿灯。
  （初稿我曾据中途版写"它没有粉饰"——那是引错了版本，结论反了。）

### 3.3 技术决策质量（从界面可见的思考过程判断）

- 放弃依赖全局 `fetch`，改用 `require('http')/require('https')`，理由：避免 Node 版本风险
- 选 CommonJS 而非 ESM，理由：兼容面更广
- **API Key 只留在服务端代理**，明确写"must not expose it in the browser"
- Markdown 渲染放弃正则链、改行级状态机，理由：cleaner and more correct
- 流式渲染用 `requestAnimationFrame` 节流，避免逐 chunk 重渲染整条消息

## 五、卡顿：本轮结论与探针缺口

### 5.1 硬数据

| 指标 | 本轮（v0.13.77，20.5 分钟） | 事故基线 |
|---|---|---|
| `[watchdog]` 事件循环停滞 | **0 条** | 166 条 / 累计 635 秒 |
| 长任务已完成（慢块告警） | **0 条** | — |
| 负载形态 | 57 轮工具调用、10 个文件变更、真实服务启动、SSE 流式、多轮模型长回复 | 多轮长会话 + `agents:list` 664 对进出 |

- 基线窗口的准确时间是 **2026-09-19 20:50:32–21:02:08（CST）**（初稿写"21:00–21:09"不准，那 9 分钟只有 23 条 / 106 秒）。
- 界面读数（**非日志字段**，来自截图）：3.35M tok + 3.35M、缓存命中 99%、思考占比 51%。
- 日志侧可核的规模：`对话完成 rounds:57, changedFiles:10`。

### 5.2 结论口径

**「在本次覆盖的负载形态下未复现」，不是「卡顿已修好」**（D-121 钉死）。

本轮相对上一轮**新排除了什么**（D-121② 要求必须写清）：
排除了"**多轮工具链 + 真实进程启动 + 文件批量写入**"这一组合是充分条件 —— 它跑满了 57 轮工具调用
仍未触发停滞。事故至今**没有被任何一轮测试稳定复现过**。

### 5.3 ★ 探针的缺口：本轮拿不到"探针是否在响"的证据

这是**关于埋点本身**最重要的发现：

`traced` / `tracedMs` / `dropped` 三个自检字段**只在停滞告警发生时才输出**
（`src/main/watchdog.ts` 里唯一的输出口就是那条告警；`peekTracedBlocks()` 只被测试引用）。
本轮停滞 0 条 ⇒ 这三个字段一次都没打印 ⇒

> **"0 条停滞"目前无法区分"确实没卡"与"探针没记账"。**

启动日志只能证明"装上了"（两条都通过，含调用方视角回读）：
```
[INFO] [sync-trace] 同步 FS 插桩已装上 18 个函数
[INFO] [sync-trace] 同步 FS 插桩经调用方视角复核生效 18 个
```
"装上"≠"这一小时里一直在记账"。**这正是我在 D-122 里刚记过的同类错误**：
校验器的读数必须度量"我在防的那件事"，而不是度量"我做的那步动作"。

**✅ 后续（同日 13:45，`80b0f25`）**：心跳已落地（每 5 分钟一条 INFO，带
`blocks`/`ms`/`total`；自启动零记账时改报 WARN），并补测拿到读数：

```
[INFO] [watchdog] 插桩心跳（探针存活证据） {"blocks":109,"ms":43,"total":109}
```

⇒ 探针确实在记账，同期停滞 0 条 ⇒ **本轮"未复现"是有分量的负证据，不再是"没有证据"**。
⇒ 顺带一个事实：空闲态 5 分钟 109 笔同步块合计仅 43ms（占 0.014%），**同步 fs 不是负担**。

⚠️ 补测过程中又踩一次同类错：先把"退出时补一次心跳"写进 `stopWatchdog()`、**单测也过了**，
真机优雅退出才发现 `stopWatchdog` 在生产代码里**零调用点** ⇒ 死代码，已删
（每条心跳都带 `total` 累计值，本来就不需要退出那一次）。
**本轮第四次踩"测了函数、没测通路"** —— 教训与立规见 `NOTEBOOK/learnings.md` 同日 03:55 条后续。

### 5.4 ✅ 时间差已闭合：带心跳的包重跑一轮（14:09–14:24，15 分钟）

上面那个"实测那 20 分钟无心跳读数"的缺口，已用**含心跳的新包**（重出 0.13.77，asar 特征串核过）
补测。任务书专挑三类嫌疑混合：大文件逐段读 + 写 12.8KB 解读文档 + 浏览器访问 nodejs.org。

```
06:14:30  blocks:1584  ms:899  total:1584    ← 负载期（读文件、写文档、窗口化）
06:19:30  blocks:0     ms:0    total:1584    ← 任务跑完等模型，真空闲
06:24:30  blocks:1410  ms:812  total:2994    ← 反思（ACE 复盘）阶段又起来
```
**同期：事件循环停滞 0 条、长任务告警 0 条。**

这个中间点 `blocks:0` 比两头更有价值，它同时证明了两件事：
1. **心跳读的是增量，不是累计** —— 若读累计，"零记账 ⇒ 探针失效"那条 WARN 判据永远不会触发，
   是个假信号。现在知道它**可达**。
2. **探针的读数有分辨力** —— 空闲 0、负载 1400～1600 笔，说明它真的在跟随系统活动，
   不是一个恒定输出的装饰。

⇒ 于是本轮的结论可以说到满了：**15 分钟、2994 笔同步块被如实记账，期间一次停滞都没有。**
⇒ 算术：负载期同步 fs 合计占 899/300000 ≈ **0.30%**；1584 笔里最大一笔也没到 500ms
（否则会有"长任务已完成"）。**普通同步文件 IO 不是那 635 秒的成因，这条被排除了。**
⇒ 剩余嫌疑收窄到：未插桩的纯计算（`JSON.parse` 大正文、字符串拼接）、
磁盘被外部占住的偶发慢 IO、以及 `log.ts` 里 stringify + scrub 那段（仍在面外）。
