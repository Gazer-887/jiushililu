# 记忆索引与故障恢复

## 正文与索引的分工

记忆正文保存在Markdown文件中；全文索引是可从正文重新生成的SQLite FTS5缓存。索引不授予读取正文的许可，recall按明确名称从生效集合回取正文。8KB提示词预算只决定本轮注入多少目录，不限制完整生效记忆的检索或按名回取。

0.13.101使用正文加载的同一资格判断：候选、已拒绝、归档、硬拒内容及被最新画像替代的旧档不进入索引；确认档与标记档沿用既有规则，仍生效且显示待过目提示。外部新增、修改和删除在下一次全文查询前复核；应用内写入、删除、归档、恢复后同步。

## 出错时会发生什么

正常检索零命中、用户关闭索引、索引不可用是三种状态。索引故障时recall返回“全文检索暂不可用”，不能据此断言没有相关资料。已知精确名称仍可取正文。

缓存故障不会把已经成功的正文写入、删除、归档或恢复变成失败；正文磁盘操作本身失败仍报错。故障后索引在本次进程内保持不可用，避免反复触碰坏库。应用不会自动删除缓存或正文。

## 手动恢复专用缓存

1. 关闭九十里路并确认其进程已退出。
2. 找到本应用的数据根目录。默认装配中fts.db与notes目录同级；如果使用自定义索引路径，先确认它属于本应用。
3. 将专用fts.db以及存在的fts.db-wal、fts.db-shm一起移到本机备份目录。保留notes、memory、meta.json和其他正文、候选、归档、事件文件。
4. 重新启动。应用按完整生效正文重建缓存，再次查询验证相关名称；若仍不可用，检查数据目录可写性与应用日志中的索引阶段及固定格式错误码（例如SQLITE_NOTADB）；日志不回显原始异常正文或路径。

以上是用户可按需执行的恢复步骤；自动测试只操作独立临时数据目录，不迁移或损坏真实用户数据。

## 可复现验证与性能边界

仓库根运行：

```sh
npx vitest run tests/unit/memory-fts-lifecycle.test.ts --config config/vitest.config.ts
npx vitest run tests/bench/memory-fts.bench.ts --config config/vitest.bench.config.ts
```

回归使用真文件系统和真SQLite，覆盖硬拒、画像、外部变更、归档恢复、初始化/运行故障、告警接收方异常和正文磁盘失败。合成数据不含真实凭据；工具链模拟不等于真实模型评测。

手动基准固定100条、每条约4KB正文，FTS开/关分别热缓存取30样本，R7计算中位数和P95。list45ms/save80ms沿用现有记忆基准的回归警报线，在首跑前登记；这不是跨机器性能承诺，也不是S147全部参数校准。启动和搜索耗时仅作诊断，不设未校准的合格线。可用JSL_MEMORY_FTS_BENCH_OUT指定原始JSON输出路径。

2026-10-09本机Windows x64、Node v24.17.0首轮测量（30样本，正文4095字节）：

| 模式 | 列表中位ms | 保存中位ms | 查询中位ms | 启动ms |
|---|---:|---:|---:|---:|
| FTS关闭 | 9.48 | 12.23 | 0.005 | 7.42 |
| FTS开启 | 8.43 | 58.90 | 15.10 | 141.62 |

两模式分别运行，列表差异可能来自机器波动，不能解释为FTS让列表变快。开启FTS的保存包含完整快照与事务更新的额外成本；当前未超既有警报线，因此保留简单方案。原始样本可按上述环境变量重新输出；本表不是通用性能承诺。

设计参考：[SQLite FTS5](https://www.sqlite.org/fts5.html)、[SQLite事务](https://www.sqlite.org/transactional.html)。事务替换防止半份缓存，应用层资格与正文保护仍由代码和回归负责。
